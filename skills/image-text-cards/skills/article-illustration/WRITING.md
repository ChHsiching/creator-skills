# WRITING.md — 写作、翻译、排版细则

`SKILL.md` 的两条硬规则（faithful / no AI tone）展开到这里。卡片正文、caption、README 都适用。

## 翻译本土化

源是英文时，中文版要像中文，不是把英文词换成中文字。

**专有名词、书名、术语**：查官方中译，凭感觉造词是失败。`The Pragmatic Programmer` 是《程序员修炼之道》（中信社中译），`tracer bullets` 是「曳光弹」（同书官方译名 + 剑桥词典）。拿不准就查；查不到就在中文后括注英文原文，让读者自己判断。

**不词对词直译**：`Add "X" to Y menu` 不是「在 Y 加上」，是「把『X』接到 Y 的菜单上」。中文搭配要成立，读出来主谓宾齐全、不别扭。

**不乱意译导致意思变**：措辞可以变，机制的因果、结论的方向不能变。`Create backend endpoint that executes the PowerShell command` 可以翻成「写一个后端接口，调用系统命令」，但不能翻成「写个后端」把「调用系统命令」丢掉。

**原文 prompt / 代码 / 命令原文呈现**：源里的 prompt 片段、代码块、shell 命令、API 名，**复制原文**放进卡片，不翻译。要中文解读就在原文块下方另起一段解释，不在原文里掺中文。读者要复制就能复制。

**翻译官方模板/策略时的逐句核对**：翻译官方的 prompt 模板或策略段落时，写完逐句对照原文——原文每一句在中文里都有对应（不漏句，哪怕细节如「Use only documented tool input and output fields」），中文每一句都能在原文找到出处（不加句，原文只说「emit exactly [output schema]」就别翻成「按格式输出，保留 high 的」——后半句过滤是原文没有的）。

## 示例的 faithful 边界

示例（填好占位符的 prompt）是**构造**出来的，不是官方原文。三条铁律：

1. **明确标注「演示用，非官方原文」**。codeblock 的 `.label` 写「示例：xxx 的 prompt（非官方原文）」，正文和 note 里至少再提醒一次「工具名/字段/数字都是举例，替换成你的」。读者照抄必须知道哪些是官方、哪些是你造的。
2. **结构跟官方模板逐句对应**。模板有 5 段，示例就有 5 段；模板每段讲什么，示例就填对应内容。逐句核对——不能漏句（漏了「evidence needed for final answer」就是丢掉了「输出要带证据」这层），不能加句（加了原文没有的过滤逻辑、审批步骤，就是自由发挥）。
3. **具体填充值是举例，明确说出来**。工具名（`list_tickets`）、字段名（`ticket_id`）、数字（5 条、3 次重试）都是你为说明占位符怎么填而构造的，不是原文的——必须告诉读者「换成你的」。

**自检**：写完示例，把官方原文和你的示例并排，逐句对照。任何一句「原文有、示例没有」或「示例有、原文没有」都是问题。

## 比喻自解释

每个比喻词第一次出现就要打开，让读者光看这个词也懂。

**反面**：「先做一条从顶到底的细线」——「顶」「底」「细线」全是生造指代，读者不知道是什么的顶、什么的底。

**正面**：「先做一个最小但完整的功能——从用户能点的界面按钮，到后台处理，到真正读写数据库」——比喻词「最小但完整」自带解释，紧跟的具体链路把「最小」「完整」落到实处。

**自检**：把比喻词单独拎出来，一个不懂这个概念的人能不能猜到意思？猜不到就要补解释，或者换一个能自解释的词。

## 用词：平实陈述

下笔前先问一句：**这页写给谁看？** 小红书的受众不是你的同行，是你的读者。讲进程泄漏给运维听、讲育儿给妈妈听——同一句话在两个语境里读起来不一样。先定位读者画像，再用**读者已经认识的词**下笔。

这条管两类常犯的错：

**第一类：把术语硬塞中文，造出读者没见过的词。** `extrapolate` 写成「别外推」，统计/机器学习以外的人读不懂；`workaround` 写成「救急方案」可以，但混进正文当动词用（「当 workaround」）就突兀。要么换读者认识的词，要么第一次出现就解释。

**第二类：把一整句话压成几个字的缩写。** 「并发 shell 调用」「反复取消命令」「超大输出」堆在一起，读者要停下来猜这是什么。本来一句话能说清的，展开说：「让 Codex 一次跑好几条命令」「卡住了反复点取消」「输出特别长的命令」。

**专业术语本身不是问题——讲进程泄漏就该有 `taskkill.exe`、`DWM`、`WMI`、`MSIX 包`，去掉反而不专业。** 但读者不和你同一个方向，你以为通用的词他们未必懂。所以术语第一次出现时括注中文：`DWM（桌面窗口管理器）`、`WMI（Windows 管理规范）`、`MSIX（Windows 应用打包格式）`。再出现只写缩写即可。

**自检**（写完每段都过一遍）：拿一个典型读者代入——「他/她看得懂这句话吗？」看不懂，是用了生造词或缩写——展开、解释，或换成日常词。拿不准读者画像时，按「外行但聪明」下笔：不要假设他懂行话，但可以假设他愿意想。

## 用词：正文不比喻

隐喻是给插画用的——那张图本身就是隐喻。**正文用字面意思。**

字面意思 = 用准确的名词、动词、数字直接陈述。「287 个 taskkill 进程，全部是 ChatGPT.exe 的直接子进程」就是字面陈述——读者读到的每个词就是它本来的意思，不需要二次「领会」。

警惕为追求生动而生造的口语比喻：把进程树说成「全挂在一个爹身上」、把失败说成「祭天」、把出问题说成「翻车」——这些词和你要讲的事实之间没有内在关联，读者要停下猜你指什么。靠选准的动词和具体细节，不靠比喻词。

**自检**：正文里每句话拎出来，是不是字面意思就能懂？需要「领会」一下才懂的，多半是塞了比喻——改成字面陈述。

## 句子完整

**主谓宾齐全**。不留「在……加上」「也是配上的」这种搭配残缺、主语缺失的句子。写完一段读出声，卡壳的地方就是病句。

**破折号克制**。一段里出现两个以上破折号，多半是把该断句的地方硬连起来了。换成句号断开，或用括号收纳插入信息。手机屏幕窄，破折号串起来的长句换行后更难读。

**句末标点齐全**。每句结尾有句号/问号/感叹号。列表项可以不加，正文段落必须加。

## 强调手段（粗体 / 高亮 / codeblock）

手机屏幕小，一段平铺没重点，读者扫不出关键。两种强调手段，各管各的事：

- **`<span class="hl">`（橘色加粗）**：用于**结论性的整句或短语**——一段里你最想让读者记住的那句话。一段最多 1 处。
- **`<b>`（黑色加粗）**：用于**段内的关键词、英文术语、核心限定词**——读者扫一眼能抓到的重点词。一段 1-2 个为宜。

### 强调的纪律

- **原文 codeblock 内不加强调**。codeblock 是原文照搬（英文 prompt、代码、命令），里面加粗会破坏原文的干净，也容易让读者误以为加粗的部分是「重点」而非「全文」。原文该什么样就什么样。
- **翻译 codeblock 内也不加粗**，同理——翻译要跟原文对应，加粗会暗示「这部分比别的更重要」，失忠。
- **解释段才加粗**：在 codeblock 下方的解释段、普通正文段、note 里，把**关键词、英文术语、核心结论**加粗。这是给读者扫读用的。
- **不整句加粗**。整句加粗等于没加粗（都是重点 = 没重点），还让版面变重。挑词加粗。
- **不滥用**。一段全是粗体，跟一段全无粗体一样糟。目标密度：一段 1-2 个粗体词 + 至多 1 处橘色高亮。

### 自检

写完一页，眯眼扫一遍正文：重点词能跳出来吗？还是糊成一片（加粗太少）/ 满屏粗体（加粗太多）？codeblock 里有没有不该有的加粗？

## 小红书发布格式（caption.md）

**不用 markdown**。小红书正文不渲染 markdown：`**加粗**` 显示成星号乱码，反引号显示成反引号。caption 正文平铺即可，强调靠分句和换行，不靠格式符。

**段落间距按手机观感**：
- 联系不紧密的两段之间隔一个空行（手机上短句就占好几行，不隔会糊成一片）
- 列表项、问答句之间贴在一起（紧密，不隔空行）
- 最紧密的几句放同一段

**英文术语标注**：英文术语第一次出现时，中文译名后括注英文（`曳光弹（tracer bullets）`）。再次出现只写中文，不重复括注。

## AI 腔识别清单

写完读一遍，命中下面任一条就改：

**结构性元话**：首先 / 其次 / 再次 / 最后 / 总而言之 / 综上所述 / 值得一提的是 / 由此可见 / 不难看出

**互联网黑话**：赋能 / 抓手 / 闭环 / 链路（当 buzzword 用时）/ 心智 / 颗粒度 / 全链路

**AI 自言自语**：原文照搬 / 整理自…… / 锁定记忆 / 让我们一起 / 我们来看 / 接下来我将 / 如下图所示（图就在下面）/ 如图所示

**跨页承接元话**：「上一页是英文原文，这一页翻成中文」「下面逐段翻译」「接下来拆给你看」「配一个填好的例子」（如果没配就别提）。这类话是 agent 给自己的施工备忘，不是读者要看的——读者翻到这页直接读内容就知道在讲什么，不需要你预告这页是干嘛的。页与页之间靠**内容逻辑**串联（02 是英文原文、03 是中文翻译，读者自己看得出关系），不靠元话预告。page-text 模板的 `LEAD` 字段经常踩这个坑——要么留空，要么只放真正的结构索引（比如「三段分别对应『只看、能改、必须先问』三类请求」这种点出结构的话），不写「这一页要做什么」。

**重复正文的补充段**：正文已经说清的事，又在结尾加一段「注：……」「另外：……」重复一遍。典型是解释完一个概念，再加「注：X 是 Y 的容器进程」——前面那句已经把 X 和 Y 的关系讲清了，「注」是冗余。写完一段，问「这段是新增信息，还是把上面的换个说法再讲一遍？」后者删掉；前者保留但融进正文逻辑位置，不要单独起「注」段。


**叠加形容词**：「高效、便捷、强大」「简单、易用、直观」——挑一个最准的，删掉其余。

**生硬转折**：「然而」「不仅如此」「与此同时」——多数情况换成正常连接词或直接断句。

读到一句觉得「这不像真人会说的话」，就重写。真人说话有节奏、有省略、有口气，AI 腔是匀速的、填满的、每个 slot 都有词。

# IMAGE-PROMPTS.md — 生图 prompt 规则、失败应对、验证

SKILL.md 的 Step 4 调用生图时读这一份。覆盖三件事：**怎么写 prompt**、**失败了怎么办**、**生完怎么验证**。

每张内容页插图的 prompt 骨架在 [`templates/image-prompt.md`](templates/image-prompt.md)。这里讲怎么填那个骨架，以及填错之后怎么办。

---

## 怎么写 prompt（硬规则，踩过的坑）

**背景色用精确 hex**（如 `#FBF7EE`），并强调 "match this exact hex precisely"。**绝不**用 cream/beige/warm/暖米 这种暖色联想词——模型一看到就往黄里渲染，"not yellow" 的否定压不住正面词。

**小黑是 small solid-black blob**（小球/小团块），**不是**大的人形角色。大 humanoid 占地方、跟信息密度打架。每张图都强调 "a blob, NOT a big humanoid"。

**小黑身上不写任何文字**。模型常自作主张在角色脸上写"小黑"两字——prompt 里明确 "Do NOT write any Chinese characters on 小黑's body or face"。

**一张图只讲一个核心结构**；小黑必须做**核心动作**（去掉小黑隐喻就不成立 = 不合格）。

**每张图重新发明一个低科技隐喻**，不能套用别页的隐喻，也不能照搬示例。

### Prompt 复杂度上限（实测 GLM-Image 经验）

- **元素清单 ≤ 5 个**。超过 5 个不同物件时，GLM-Image 等后端常返回空 url（生成失败）。把多元素对比（如三行矩阵、多格分镜）**拆成单隐喻单画面**，或把次要元素移到卡片正文。
- **每段描述 ≤ 2 句**。整篇 prompt 总长控制在 60 行内。冗长的 composition 描述会触发后端 token 超限或内容过滤。

## 失败了怎么办（区分两类失败）

生图失败有两类，应对完全不同——`gen_image.mjs` 已经自动区分，但 agent 写 prompt 时也要知道：

### 限流失败（HTTP 429 / rate limit / 「速率限制」）

**现象**：返回 `HTTP 429` 或错误信息里有「速率限制/limit/too many requests」。

**应对**：`gen_image.mjs` 自动退避重试 3 次（30s / 60s / 90s）。配额按时间窗口恢复，等够就过。如果 3 次都失败，等几分钟再跑，或批量时用 `--delay` 串行间隔：

```bash
# 批量生图，每张间隔 25 秒避免限流
for p in 01-foo 02-bar 04-baz; do
  node scripts/gen_image.mjs prompts/$p.md illustrations/$p.png --size 1280x736 --delay 25000
done
```

### 内容失败（empty url / HTTP 400 / 隐喻被误读）

**现象**：返回 `no image url in response`、HTTP 400，或**生成了但隐喻画歪了**（比如要方括号 `[ ]` 画成了勾选框，要"汇流"画成了"拿铅笔"）。

**应对**：不要原样重发同一个 prompt（大概率还失败）。改 prompt：

1. **元素太多** → 砍到 ≤ 4，合并多面板结构成单隐喻，段落缩到 ≤ 2 句。
2. **隐喻被误读** → 换隐喻载体。模型对某些视觉概念有顽固误读：
   - `[ ]` 方括号常被画成勾选框 ☐ → 改用"下划线填空表"（`_____`）
   - "三条路线汇流" 可能画成"拿笔写字" → 改用"多条溪流汇入窄口锅"
   - 抽象动词（"授权""边界"）画不出来 → 换成具体物件（三档开关、锁门）

## 生完怎么验证（治"agent 看不见图"）

生图后 agent 没法直接"看"图（Read 工具只回 CDN URL 文本）。**必须用图像分析工具核验**，不能假设生成了就是对的了。

### 验证清单（每张插图都过一遍）

用 `analyze_image`（或等效图像分析工具）对生成的插图问这几个问题：

1. **小黑是 blob 吗**？是不是被画成了大 humanoid（人形）？
2. **小黑做的是核心动作吗**？还是要表达的隐喻没体现、小黑成了装饰？
3. **小黑身上/脸上有文字吗**？（模型常自作主张写"小黑"）
4. **背景色对吗**？是 `#FBF7EE` 浅暖中性，还是发黄了？
5. **隐喻成立吗**？画面是不是把概念画歪了（见上文的"隐喻被误读"）？
6. **有渲染失败吗**？模糊、乱码、空白、角色缺失？

任一项不过 → 按上文"内容失败"的应对改 prompt 重生。

### 批量验证的省力做法

6 张图逐张分析费时。可以批量并行调用 `analyze_image`，每张只问这 6 个问题（短 prompt），拿到结果再决定哪张要重生。

### 验证读到的是旧图（CDN 缓存）

**现象**：你刚改了 prompt 重生图，但 `analyze_image` 描述的还是上一版（描述里出现「这次没改的字」「旧版本的元素」）。

**根因**：Read 工具返回的图是 CDN URL，分析工具按 URL 缓存——同 URL 的请求可能拿到旧版本，即使文件已经换了。

**解法**：验证前，让 Read 返回**新**的 CDN URL（重新 Read 同一个文件路径，URL 里通常带新的时间戳/签名），或给 URL 加一个递增的 cache-buster（`?cb=N`）绕开缓存。改完 prompt 重生后，**重新 Read 再分析**，不要复用上一轮的分析结果。

## 结构类型参考（Composition 填写时选一种）

| 结构 | 适合 | 画法要点 |
|------|------|----------|
| Workflow 流程 | 输入→处理→输出 | 左输入/中小黑处理/右输出，橙色箭头表达流向 |
| 系统局部 | 信息来源/过滤器/agent 局部 | 只画 3-5 核心模块，小黑参与其中一个关键动作 |
| 前后对比 | 混乱/有序、手动/自动 | 左右两段，中间橙色箭头 |
| 角色状态 | 痛点/卡住到跑起来 | 2-4 个小状态，每个一个短标注 |
| 概念隐喻 | 工厂/黑盒/工作流机器 | 一个大怪物件，少量输入一个输出，要有记忆点 |
| 方法分层 | 框架/层级/能力栈 | 一层层盒子，不要正式金字塔 |
| 地图路线 | 从想法到上线/路径 | 一条弯曲路径，少量节点，小黑牵线或走路 |
| 过程演示 | 累积/递进/阈值 | 同一物件多个递增状态，箭头串联 |

**隐喻要"机制自洽"**：画面的外壳必须直接体现概念机制，而不是贴个标签硬说。
- 反例：小黑推煤车 + 一条虚线标"140K"——煤车和"变笨"没内在关联，看不懂。
- 正例：小车从少→满→溢出三段——"装不下就洒了"直接演示了"多了会出错"。

## 颜色规则

- 橙色 = 主路径/箭头/从 A 到 B 的流向
- 红色 = 重点/问题/结果/警戒线（只用在一处）
- 蓝色 = 补充说明/系统状态（可选，不是每张都要）
- 黑色 = 主体线稿、小黑、框线、主要文字

颜色克制，宁可少不要多。
